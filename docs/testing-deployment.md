# 06. 테스트, 검증 및 Vercel 배포

## 1. 테스트 환경
- 로컬 Node.js LTS
- Vercel CLI 또는 실제 Vercel Preview 배포
- 별도 개발용 OpenAI 및 Supabase 프로젝트/키 사용 권장
- 실제 키는 테스트 코드나 문서에 기록하지 않는다.

## 2. 기능 테스트 케이스

| ID | 입력/상황 | 기대 결과 |
|---|---|---|
| T-01 | "오늘 정말 행복하다" | positive, 결과 카드 표시 |
| T-02 | "최악의 하루였다" | negative, 결과 카드 표시 |
| T-03 | "회의는 오후 3시에 시작한다" | neutral 분류 가능 |
| T-04 | 빈 문자열 | 400 또는 프런트 입력 안내, AI 호출 없음 |
| T-05 | 공백만 입력 | 입력 거부 |
| T-06 | 5,001자 입력 | 입력 거부 |
| T-07 | 서버에 5,001자 직접 전송 | 서버가 거부 |
| T-08 | 잘못된 JSON | 400 INVALID_JSON |
| T-09 | GET 요청 | 405 |
| T-10 | OpenAI 키 누락 | 서버 오류, 키 정보 미노출 |
| T-11 | OpenAI timeout | 사용자 친화적 오류 |
| T-12 | 모델이 잘못된 레이블 반환 | MODEL_INVALID_RESPONSE |
| T-13 | Supabase insert 실패 | 분석 결과는 정상 반환 |
| T-14 | 연속 클릭 | 중복 요청 방지 |
| T-15 | 모바일 viewport | 가로 스크롤 없이 사용 가능 |

감성 예시 테스트는 모델의 결과가 항상 특정 레이블이어야 한다는 보장이 아니라, 정상 응답·표시·스키마 검증을 확인하는 테스트다. 실제 분류 품질은 별도 평가 데이터셋으로 측정해야 한다.

## 3. 추가 검증
### 보안
- 브라우저 개발자 도구의 소스/네트워크 응답에서 OpenAI 키와 Supabase Service Role Key가 보이지 않는지 확인한다.
- 사용자 입력 및 모델 생성 텍스트가 HTML로 실행되지 않는지 확인한다.
- 서버 로그에 원문 텍스트가 남지 않는지 확인한다.

### 접근성/반응형
- 키보드만으로 입력·제출·결과 확인이 가능한지 확인한다.
- 포커스 표시와 라벨이 있는지 확인한다.
- 360px 폭 모바일, 태블릿, 데스크톱에서 레이아웃을 확인한다.
- 결과 상태가 색상 외 텍스트로도 구분되는지 확인한다.

## 4. 환경변수
`.env.example`:
```dotenv
OPENAI_API_KEY=
OPENAI_MODEL=
SUPABASE_URL=
SUPABASE_SERVICE_ROLE_KEY=
```
실제 값은 로컬 `.env` 및 Vercel Project Settings의 환경변수에 입력한다. `.env`는 `.gitignore`에 포함한다.

## 5. 로컬 실행
1. 저장소 루트에서 `npm install`을 실행한다.
2. `.env.example`을 참고해 `.env`를 만든다.
3. OpenAI 및 Supabase 환경변수를 설정한다.
4. `supabase/schema.sql`을 Supabase SQL Editor에서 실행한다.
5. `package.json`에 정의된 로컬 실행 명령을 실행한다.
6. 브라우저에서 메인 페이지와 `/api/analyze`를 검증한다.

에이전트는 실제 구현에 맞춰 `package.json`의 스크립트를 정의하고 README에 정확한 명령을 기록해야 한다. 존재하지 않는 명령을 문서에 적지 않는다.

## 6. Vercel 배포
1. Git 저장소를 Vercel 프로젝트에 연결한다.
2. 환경변수를 Preview와 Production에 각각 등록한다.
3. 프레임워크 프리셋은 프로젝트 구조에 맞는 정적 사이트/기본 설정을 선택한다.
4. API Function이 `/api/analyze` 경로로 배포되는지 확인한다.
5. Preview 배포에서 전체 테스트를 수행한다.
6. 통과 후 Production 배포한다.
7. 배포 후 실제 도메인에서 정상 분석·오류·모바일 UI를 확인한다.
